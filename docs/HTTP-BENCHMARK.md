# Local HTTP adapter benchmark

Reproduce the full comparison: `python tools/benchmark_http.py --full-parity`. The default omits the slower full-suite step and retains the twelve bounded probes. Public receipt: [raw samples and source hashes](evidence/http-benchmark-2026-11-12.json). Full local logs: `.factory/mechanics08/benchmark.json`. The recorded source commit is the checkout base at measurement time; the benchmark candidate itself is bound by `source_sha256` rather than claimed to be tracked in that base commit.

This compares the existing `Server`/`ThreadingHTTPServer` with a bounded four-worker pool adapter (eight admitted sockets, accept backpressure), using the exact application `Handler` and `Server` initialization. It is not a new framework comparison and does not authorize switching the production server. No production source changed.

Each adapter runs in a separate child process with a fresh temporary SQLite workspace and an ephemeral loopback port. Requests are sequential, opening normal urllib HTTP connections. The measured route is `/api/bootstrap`. Five warmup requests precede 100 measured requests per adapter. Cold means the first bootstrap round trip after server initialization; it excludes interpreter/server startup. Percentiles use nearest rank. No throughput, saturation, concurrent-load or general performance advantage is established by this single run.

Memory is sampled in the child after measured requests and before shutdown. On this Windows run the native `GetProcessMemoryInfo.WorkingSetSize` supplies current resident bytes and `PeakWorkingSetSize` supplies peak resident bytes. The Linux path reads resident pages from `/proc/self/statm`; it does not pretend that peak-only resource usage is current RSS.

Twelve bounded parity probes check initial signed-out body, unknown route, wrong host, wrong CSRF, wrong origin, invalid login, protected-route rejection before authentication, successful synthetic login with expected principal, authenticated dispatch into the same protected route, session principal, successful logout and principal removal. Both adapters must match each other and independent expected outcomes. The protected dispatch probe intentionally reaches an unknown action (404 after authentication versus 403 before authentication); it does not exercise a successful owner operation. The synthetic GitHub identity verifier is patched only inside the child, and no provider request occurs. Tokens and random cookies/CSRF values are omitted from receipts.

The explicit `--full-parity` run also executed the unchanged `tests.test_http` suite in separate child processes, patching only that module's `Server` factory. Baseline: 21/21 tests passed in 35.681 seconds; bounded pool: 21/21 passed in 35.933 seconds; both had zero failures, errors or skips. These existing tests exercise actual routes, authenticated operations and CSRF boundaries. Exact test names/outcomes and full logs are retained in `.factory/mechanics08/full-suite-results.json` and embedded in the benchmark receipt. A failing/empty/skipped suite or different test count rejects the comparison before latency measurement. Full suites run before both fresh measurement subprocesses; their durations are not latency samples. This establishes the specified suite passing on these adapters, not framework parity, external identity verification, or release approval. Small synthetic state, sequential traffic, process order, caches and host noise limit interpretation. Child readiness, HTTP I/O and teardown have deadlines; the parent kills and reaps a surviving child in `finally`. The pool's queue bound is explicit but is not a measured load/saturation claim.

Validation: `python -m unittest tests.test_http_benchmark -q` covers real local servers and negative malformed timing/parity fixtures; `ruff check`, `ruff format --check`, and Pyright cover the two new sources. See the local evidence log for exact execution results.
