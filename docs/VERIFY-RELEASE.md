# Verify a downloaded preview release

Use the release's own checksum manifest; do not fetch hashes from a chat, issue or mirror. Run the repository verifier with **Python 3.11 or newer** from a source checkout; its neighboring provenance helper is required.

```sh
python tools/verify_release_assets.py --folder ./WMM-preview --source-sha <exact 40-hex source>
```

Use this verifier for releases that include both SBOMs and a checksum manifest covering all six payload files. Preview 7 and earlier have the older installer-only checksum format. Keep those releases intact and use their own checksum manifests to verify the installer bytes.

Download into one folder:

- `WMM-Setup.exe`
- `wize-marketing-machine_0.1.0_amd64.deb`
- `Windows.json`, `Linux.json`
- `sbom-Windows.json`, `sbom-Linux.json`
- `SHA256SUMS.txt`
- For the new attested release format: `release-attestation.sigstore.json` and `release-provenance.json`

The verifier fails if:

- the manifest is empty, malformed, duplicated or incomplete;
- any listed file is missing, has changed bytes, is a symlink or has an extra unlisted file;
- an installer receipt does not match the platform, asset name, source SHA, installer hash or passing lifecycle evidence;
- an SBOM is not CycloneDX 1.5, is not bound to the requested source SHA, or is not labeled `build_environment`;
- the downloaded folder contains an unexpected file.

It prints a JSON `PASS` only after every check. This verifies downloaded bytes and metadata; it does not prove code signing, reproducible builds, provider behavior or human first use.

## Verify GitHub artifact provenance

For releases produced after the provenance verification gate was added, use the
official [GitHub CLI attestation verifier](https://cli.github.com/manual/gh_attestation_verify)
on each of the six payload files above. Set `SOURCE_SHA` to the exact reviewed
40-character source commit, then run this command with each payload's file path:

```sh
gh attestation verify ./WMM-preview/WMM-Setup.exe --hostname github.com --repo zrk222/WMM --signer-workflow zrk222/WMM/.github/workflows/desktop-release.yml --source-digest "$SOURCE_SHA" --deny-self-hosted-runners --format json
```

Repeat for the Debian installer, both platform receipts, and both SBOM files.
Require a successful exit and nonempty verified-attestation results for every
payload. The repository, signer workflow, and exact source constraints must stay
present. The default predicate is SLSA provenance v1. For the new release format, add `--bundle ./WMM-preview/release-attestation.sigstore.json` to verify the downloaded bundle itself. Keep the repository, signer-workflow, exact source and hosted-runner constraints. This cryptographic check is separate from the offline checksum verification above.

`SHA256SUMS.txt` is generated by the publisher after these six payloads are
attested and verified; the checksum file itself has no provenance attestation.
An SBOM payload's build provenance is separate from an SBOM-specific attestation:
the JSON remains a build-environment inventory, not a runtime inventory.

The new release workflow includes the exact verified Sigstore bundle and a source-bound `release-provenance.json` receipt in the public download. The receipt records the complete official verifier outputs for all six payloads, their hashes, bundle hash, source SHA and verification constraints. `SHA256SUMS.txt` covers these two evidence assets as well as the six payloads. The checksum manifest and verification receipt are not recursively attested.

The offline verifier accepts the exact legacy seven-file set or the new nine-file set; for the latter it checks bundle/receipt/hash bindings and reports cryptographic verification as not run. Use the official `gh attestation verify --bundle` command for cryptographic verification. Run the repository verifier from a checkout so its neighboring helper is available.

The release workflow retains a source-bound verification receipt before
publishing. This proves the official verifier admitted those staged payload
bytes under the declared constraints. It does not provide a Windows publisher
signature, remove unsigned-installer trust prompts, prove reproducible builds,
or establish human first-use acceptance. Earlier previews without these
attestations retain their existing checksum and unsigned-preview limits.

For a Windows release advertised as publisher-signed, independently check the
downloaded installer in PowerShell:

```powershell
$signature = Get-AuthenticodeSignature -LiteralPath .\WMM-Setup.exe
$signature.Status
$signature.SignerCertificate.Subject
$signature.SignerCertificate.Thumbprint
$signature.TimeStamperCertificate
```

Require `Valid`, a timestamp certificate, and the expected publisher identity
and certificate thumbprint from the release's provenance-verified `Windows.json`
(`lifecycle.publisher_signature.thumbprint`). Preview 9 and earlier do not
provide this publisher evidence.
